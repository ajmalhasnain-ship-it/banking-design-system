Banking Design System

A design system built from one token source. It covers two platforms, light and dark themes, and more than 80 components. Banking was the test case because it needs dense data, visible trust and strong accessibility.

Why banking

The hardest version of the problem

A banking app combines almost every hard UI case. Tables and charts have to stay readable when they are full of data. Small visual details affect whether people trust the app. Accessibility can't be skipped. Many people check their money late at night, so dark mode matters too.

If a system works here, it will work in simpler products.

Foundations · Colour

Colours by role, not by hex code

There are nine colour families. Each has eleven steps, and the neutral (mono) ramp has fourteen. Components never use a hex value directly. They use semantic roles such as primary, surface, border and disabled. Each role points to a different ramp step in each theme, so switching themes is a single toggle.

Fig. 01: Sample colour ramps. Every foreground/background pair was checked against WCAG contrast in both themes.

States

Every interactive part has every state

Every interactive component has five states: enabled, hover, active, focus and disabled. Each state comes from tokens, so developers never have to guess how a hover should look.

Library

From chips to charts

The library starts with small pieces like chips, badges and avatars. It goes up to complex ones such as data tables, charts, date-range pickers and file upload. To test it, four complete pages were built using nothing but system parts.

  • DashboardBalances, recent activity and quick actions
  • CalendarScheduled payments and date-range selection
  • UploadDocument upload, with progress and error states
  • StatisticsSpending charts and comparisons by category

Dark mode

Solved once, at the token level

Dark mode isn't a second set of designs. Colour, contrast, shadows and states all come from variables, so every screen works in both themes without fixing screens one by one.

Honest limits & next steps

What's still missing

No product team has used the system yet, so there is no adoption data. The next steps are:

  • Token exportGenerate JSON tokens that developers can use directly
  • VersioningSet up a release and change-log process
  • Second productBuild a different product with it to check that it holds up
